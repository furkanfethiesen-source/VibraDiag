# Decisions

This document is used to record important technical and architectural decisions made during the project.

---

## 1) Self-Corrector: Reducing Dual LLM Calls to a Single Call and Threshold Calibration
**Decision:** Faithfulness and Relevance checks were combined into a single `UnifiedJudgeChecker` LLM call. Threshold values were determined through grid-search calibration on the benchmark dataset. Low rerank score chunks were selectively excluded to preserve context quality.

**Reasoning:**
- Two separate LLM calls (Faithfulness + Relevance) doubled token costs and latency.
- When the self-corrector was overly strict, every draft was rejected, reaching the max cycle limit; threshold values (`faithfulness: 0.50`, `relevance: 0.50`) were optimized through calibration.
- Selectively excluding only chunks with `score < chunk_exclusion_threshold (0.25)` instead of dropping all chunks prevented context degradation over iterations.

**Alternatives considered:**
- Two separate LLM calls (Faithfulness + Relevance separately) — high cost and latency.
- Fixed threshold values — overly strict or loose across different query types.
- Excluding all chunks — caused context impoverishment and information loss.

**Consequence:**
- Token costs and latency were cut in half.
- Frequency of reaching the max cycle limit decreased.
- The self-correction loop became more stable while maintaining context quality.
- Related files: `checkers.py`, `corrector_node.py`, `corrector_evaluator.py`, `app.yaml`

**Status:** Confirmed

## 2) Reranker: Gradual Soft-Fallback Mechanism
**Decision:** A 3-tier soft-fallback mechanism was added to the cross-encoder reranker: standard threshold filtering (`≥ 0.20`), soft-fallback floor (`≥ 0.10` + warning log), and unconditionally preserving the top-1 candidate as a last resort.

**Reasoning:**
- Applying a strict threshold eliminated all candidates for certain difficult queries, resulting in context starvation.
- Completely removing the threshold allowed low-quality chunks to pass to generation.
- The gradual fallback eliminates context starvation risk while maximizing quality.

**Alternatives considered:**
- Single fixed threshold — risk of context starvation as all candidates could be dropped.
- Pass-through without threshold — low-quality chunks leak into generation.

**Consequence:**
- Context starvation is prevented for all queries; in the worst case, the top-1 candidate is preserved.
- When soft-fallback triggers, a warning is logged — increasing observability.
- Related files: `reranker.py`

**Status:** Confirmed

## 3) Decomposer: Max Sub-Query Overflow Protection
**Decision:** If the number of sub-queries generated by the LLM exceeds `max_sub_queries + 1` (≥2 excess), it is treated as severe hallucination and falls back to simple retrieval. If it is exactly 1 in excess, the last query is trimmed down to `max_sub_queries`.

**Reasoning:**
- The LLM occasionally produced 7-8 unnecessary sub-queries, which degraded retrieval quality and increased costs.
- Generating 1 excess sub-query is treated as "mild hallucination" and tolerated via truncation; generating 2+ excess is considered severe drift and canceled.
- Configuration: `max_sub_queries: 3`, `min_sub_queries: 2`.

**Alternatives considered:**
- Silently trimming all excess sub-queries — overlooked severe hallucinations.
- Completely aborting on any excess — lost tolerable cases like 1 excess sub-query.

**Consequence:**
- Mild hallucinations are tolerated, while severe ones are caught early.
- The system continues operating without crashing thanks to the simple retrieval fallback.
- Related files: `llm_decomposer.py`

**Status:** Confirmed

## 4) Dynamic Top-k Based on Sub-Query Count
**Decision:** In parallel sub-query retrieval, the rerank top-k allocated to each query is dynamically calculated by dividing the total budget (`target_candidate_budget: 35`) by the number of sub-queries: `per_query_rerank_top_k = max(min_per_sq, ceil(target_budget / sub_query_count))`.

**Reasoning:**
- With a fixed top-k, 3 sub-queries resulted in an excessively large total candidate pool, whereas 1 sub-query resulted in too few.
- Dynamic distribution maintains a constant total candidate budget while providing a fair allocation to each query.
- Minimum quality is guaranteed with `min_candidates_per_subquery: 8`.

**Alternatives considered:**
- Fixed top-k (e.g., top-10 per query) — total candidate count varies unevenly with the number of sub-queries.
- Fixed total budget concentrated on the first N queries — fails to provide fair distribution.

**Consequence:**
- The total number of candidates entering the reranker is controlled and predictable.
- Prevents unnecessary candidate explosion for queries with multiple sub-queries.
- Related files: `retriever.py`

**Status:** Confirmed

## 5) Decomposer Router: Logistic Regression Classifier
**Decision:** A lightweight `LogisticRegression` pipeline was chosen as the query complexity classifier for the MVP stage. The pipeline uses word TF-IDF (1,3), char TF-IDF (2,5), and handcrafted lexical features (`LexicalFeatures`). Confidence threshold: `0.55`.

**Reasoning:**
- An LLM-based router required an additional inference call for every query — increasing latency and cost.
- Logistic Regression runs in milliseconds and provides sufficient accuracy for binary classification.
- Sufficient for MVP; leaves room for migration to more powerful models in the future.

**Alternatives considered:**
- LLM-based router (extra inference per query) — high latency and cost.
- Rule-based router (keyword matching) — insufficient for edge cases.
- Transformer-based classifier — overkill and slower.

**Consequence:**
- Routing decisions are made in milliseconds without impacting overall pipeline latency.
- Rare false positives/negatives may occur in complex multi-fault queries.
- Related files: `classifier.py`, `node_factories.py`

**Status:** Confirmed

## 6) Parent Chunk Deduplication Mechanism (Toggleable)
**Decision:** Child chunks sharing the same `parent_id` are deduplicated at the output of the reranker. The mechanism can be enabled/disabled via the `deduplicate_parents: bool = True` parameter.

**Reasoning:**
- When multiple child chunks belonging to the same parent chunk were retrieved, redundancy was introduced into the context passed to generation.
- During evaluation, deduplication needed to be toggleable to test different retrieval scenarios.
- The toggle mechanism provides flexibility for both production and evaluation.

**Alternatives considered:**
- Always-on deduplication — loses evaluation flexibility.
- No deduplication — duplicated parent chunks in context lead to token waste.

**Consequence:**
- Parent diversity in the context increases, reducing token usage.
- The effect of deduplication can be measured during evaluation using `deduplicate_parents=False`.
- Related files: `reranker.py`

**Status:** Confirmed

## 7) Retrieval Subgraph: Asynchronous Architecture
**Decision:** The retrieval subgraph was implemented entirely asynchronously (`async/await`). Sub-queries are executed in parallel using `asyncio.gather`. Synchronous components (Qdrant search, reranker) were wrapped with `asyncio.to_thread`.

**Reasoning:**
- In synchronous retrieval, executing 3 sub-queries sequentially tripled overall latency.
- The asynchronous structure allows sub-queries to run in parallel, minimizing latency.
- LangGraph compiled graphs natively support async nodes.

**Alternatives considered:**
- Synchronous sequential retrieval — latency scales proportionally with the number of sub-queries.
- Thread pool executor — higher complexity and difficult error handling.

**Consequence:**
- Latency significantly reduced for multi-sub-query queries.
- Non-CPU-bound waiting is handled efficiently via the async I/O model.
- Related files: `retriever.py`, `qdrant_vector_db.py`, `reranker.py`

**Status:** Confirmed

## 8) Qdrant: Hybrid Search with Dynamic Prefetch
**Decision:** For Qdrant native hybrid search, dense and sparse vector prefetch limits are adjusted dynamically according to modality weights (`weights`). The dominant modality's limit is calculated as `n_results × 2.5`, while the other is `n_results × 1.5`. Fusion is performed using Reciprocal Rank Fusion (`RRF`).

**Reasoning:**
- Fixed prefetch limits were insufficient when either the dense or sparse modality was dominant.
- Weight-based dynamic adjustment provides more candidates to the dominant modality without neglecting the other.
- Using Qdrant's native Prefetch + FusionQuery API eliminated the need to write custom merging logic in the application layer.

**Alternatives considered:**
- Fixed prefetch limits (e.g., `n_results × 2` for both modalities) — unbalanced.
- Separate queries at application layer + manual RRF merging — more code and higher latency.

**Consequence:**
- Hybrid search quality is optimized according to the weight configuration.
- Prefetch + fusion is executed in a single Qdrant `query_points` call.
- Related files: `qdrant_vector_db.py`

**Status:** Confirmed

## 9) RAGAS + Deterministic Evaluation Metrics
**Decision:** Alongside RAGAS LLM-as-a-judge metrics (Faithfulness, ResponseRelevancy, LLMContextPrecision, LLMContextRecall), separate deterministic metrics (Recall@k, Precision@k, HitRate@k, MRR@k, NDCG@k) were added at both child and parent chunk levels for evaluation.

**Reasoning:**
- RAGAS metrics alone were insufficient to evaluate retrieval quality — LLM-as-a-judge only evaluates generation quality.
- Deterministic metrics mathematically evaluate retrieval performance at both child and parent levels.
- The dual approach allows monitoring both generation and retrieval quality independently.

**Alternatives considered:**
- RAGAS metrics only — no visibility into retrieval-specific performance.
- Deterministic metrics only — unable to evaluate generation quality.

**Consequence:**
- Child and parent retrieval performances can be tracked independently.
- Generation and retrieval quality are benchmarked separately.
- Related files: `custom_metrics.py`, `ragas_evaluator.py`

**Status:** Confirmed

## 10) DSP: Linear Parabolic Peak Interpolation
**Decision:** 3-point parabolic peak interpolation was implemented on a linear (amplitude) scale for the MVP; logarithmic (dB) scale was deferred.

**Reasoning:**
- Linear scale implementation is simpler and easier to debug.
- Since most industrial fault frequencies (BPFI, BPFO) have sufficient SNR, the linear scale provides acceptable accuracy.
- Logarithmic scale is planned for advanced analysis requiring sub-Hz precision on low-amplitude harmonics.

**Alternatives considered:**
- Logarithmic (dB) parabolic interpolation — better sub-bin accuracy in high dynamic range spectra, but higher implementation complexity.
- Increasing resolution with zero-padding — higher memory and computational cost.

**Consequence:**
- Accurate results for high-SNR faults; limited sub-bin accuracy for low-amplitude harmonics.
- Migration to logarithmic scale planned as a future improvement.
- Related files: `signal_processing.py`

**Status:** Confirmed

## 11) DSP: Hybrid 2-Stage Peak Matching (RMS + Peak Gating)
**Decision:** Instead of using standalone RMS energy or peak amplitude for diagnosis, a 2-stage hybrid approach was adopted: (1) Verifying the presence of an actual peak within the tolerance window via peak gating, (2) Calculating fault severity via Band-RMS (Simpson integration).

**Reasoning:**
- Peak amplitude alone is susceptible to noise-induced spurious peaks.
- RMS alone is insufficient for fault localization as it measures broadband energy.
- Mutual verification between the two metrics reduces false positive rates and strengthens severity assessment.

**Alternatives considered:**
- Peak amplitude only — high sensitivity to noise.
- Band-RMS energy only — can confuse broadband noise with fault signals.

**Consequence:**
- Higher reliability in fault detection (both peak presence and energy verification).
- In harmonic matching, individual Band-RMS is computed for each harmonic — providing a detailed severity profile.
- Related files: `signal_processing.py`

**Status:** Confirmed

## 12) DSP: Dynamic Tolerance Band
**Decision:** Instead of a static tolerance band, a dynamic tolerance band that expands proportionally with harmonic number and base frequency was used: `Tolerance(h) = max(min_abs_tol_hz, base_freq × h × tolerance_ratio) × (1 + α × (h - 1))`.

**Reasoning:**
- Static tolerance (e.g., ±2 Hz) was excessively wide for low-frequency faults (FTF ~12 Hz) and excessively narrow for high-frequency faults (BPFI ~162 Hz).
- Proportional tolerance automatically adapts across frequency ranges.
- The `alpha` parameter enhances capacity to tolerate natural frequency shifts at higher harmonics.

**Alternatives considered:**
- Static fixed tolerance (±N Hz) — inconsistent across different frequency ranges.
- Percentage-based fixed tolerance (±N%) — insufficient minimum window at very low frequencies.

**Consequence:**
- Appropriate matching window for all fault types (from low-frequency FTF to high-frequency BPFI).
- Adaptable to different machine types via configurable parameters (`min_abs_tol_hz`, `tolerance_ratio`, `alpha`).
- Related files: `signal_processing.py`

**Status:** Confirmed

## 13) DSP: STFT-Based Spectral Kurtosis (Fast Kurtogram)
**Decision:** STFT-based spectral kurtosis (Fast Kurtogram) was selected for optimal bandpass filter center frequency and bandwidth selection.

**Reasoning:**
- Kurtosis is the most effective statistical indicator for detecting impulsive signals.
- The STFT-based approach allows simultaneous kurtosis computation across multiple decomposition levels (`nlevels`).
- Compared to raw FFT, frequency-band optimization enhances envelope demodulation quality.

**Alternatives considered:**
- Wavelet-based kurtogram — more complex implementation with similar results.
- Manual band selection (fixed filter parameters) — inadequate across different fault types.
- FFT peak analysis only — poor performance on impulsive faults.

**Consequence:**
- Optimal band is automatically selected for bearing defect frequencies.
- Hilbert envelope demodulation quality directly depends on the kurtogram output.
- Related files: `signal_processing.py`

**Status:** Confirmed

## 14) DSP: Z-Score Protection via Noise Null-Distribution
**Decision:** To prevent pure noise from producing high kurtosis due to Rayleigh distribution and triggering false positives, the signal is shuffled `n=5` times to create a null-distribution, requiring the true peak value to be `z ≥ 3.0` standard deviations above this distribution.

**Reasoning:**
- The Fourier transform of Gaussian noise follows a Rayleigh distribution and can produce high kurtosis — leading to spurious kurtogram peaks.
- Permutation testing (comparison against surrogate signals) provides a statistically reliable test to distinguish true signals from noise.
- The z ≥ 3.0 threshold corresponds to a 99.7% confidence interval.

**Alternatives considered:**
- Fixed kurtosis threshold — variable depending on signal characteristics, unreliable.
- Bootstrap testing — slower, similar results.

**Consequence:**
- False positive kurtogram detections are prevented in noisy signals.
- 5 surrogate computations introduce ~5x additional kurtogram computation cost — an acceptable trade-off.
- Related files: `signal_processing.py`

**Status:** Confirmed

## 15) DSP: Spectral Kurtosis Edge Artifact Protection
**Decision:** When computing spectral kurtosis, the upper frequency was bounded to `(1 − 0.15) × f_Nyquist` to prevent edge artifacts and spurious peaks in the transition band.

**Reasoning:**
- Near the Nyquist frequency, anti-aliasing filter roll-off edge effects produce spurious high kurtosis.
- `nyquist_guard_ratio = 0.15` excludes the top 15% frequency band from kurtosis calculation.
- Kurtosis in these bands is set to `-inf`, excluding them from band selection.

**Alternatives considered:**
- Computation without guard ratio — risk of spurious peaks near the Nyquist edge.
- More aggressive guard (e.g., 0.25) — unnecessarily narrows the usable frequency range.

**Consequence:**
- Incorrect band selection caused by edge artifacts is prevented.
- 85% usable frequency range is preserved.
- Related files: `signal_processing.py`

**Status:** Confirmed

## 16) DSP: Misalignment Detection via Cross-Channel Phase Difference
**Decision:** Coupling misalignment is detected by identifying a `180° ± 30°` phase difference across channels at 1X/2X harmonics.

**Reasoning:**
- Angular misalignment characteristically produces a 180° phase difference across opposing channels.
- ±30° tolerance accounts for real-world industrial mounting tolerances and measurement uncertainties.
- The `check_coupling_phase` function checks all channel combinations using `itertools.combinations`.

**Alternatives considered:**
- Amplitude analysis only — cannot distinguish between misalignment and unbalance.
- Narrower tolerance (±10°) — excessive false negatives in real industrial environments.
- Wider tolerance (±45°) — risk of confusion with other fault types.

**Consequence:**
- Enables differentiation between unbalance and angular misalignment.
- Requires multi-channel data — cannot be used with single-channel measurements.
- Related files: `fault_localization.py`

**Status:** Confirmed

## 17) Vision Pipeline: Structured JSON Output Instead of Pixel-Based Embedding
**Decision:** In the vision pipeline, images are converted to structured JSON output using Gemini 3.5 Flash with `response_mime_type="application/json"` instead of direct pixel-based dense embeddings.

**Reasoning:**
- Pixel-based embedding (e.g., ColPali) is overkill and computationally expensive at the MVP stage.
- Structured JSON output parses fault types, frequency information, and visual interpretations into distinct fields.
- Output consistency is guaranteed via Pydantic schemas (`SpectrumSchema`, `OrbitSchema`, `BearingStageSchema`, `SeverityChartSchema`).

**Alternatives considered:**
- Pixel-based dense embedding (ColPali / multimodal RAG) — too complex and computationally demanding for MVP.
- OCR + regex parsing — unstructured output with high error rates.

**Consequence:**
- Structured JSON simplifies downstream processing (chunk generation, retrieval, validation).
- Minor extraction inconsistencies may occur — may require manual schema validation (known limitation).
- Migration to ColPali / Gemini Pro planned as a future improvement.
- Related files: `vision_pipeline.py`, `schemas.py`

**Status:** Confirmed

## 18) Vision Pipeline: Fault Type Cross-Validation and Error Isolation
**Decision:** The `fault_type` generated by the model is validated against original caption text and orbit shape matches using heuristic rules. In case of discrepancies, a `needs_review=True` flag is assigned. Failed images do not halt the pipeline; instead, they are isolated and logged to a `_failed.json` file.

**Reasoning:**
- The vision LLM occasionally generated fault types inconsistent with the caption.
- `_cross_validate_fault_type` checks against keywords in the caption, `_orbit_consistency_flag` checks against orbit shapes, and `_spectrum_diagram_leak_flag` checks against spectrum leak words.
- A single failed image must not halt the entire ingestion pipeline — ensuring graceful degradation.

**Alternatives considered:**
- No validation — inconsistent data degrades retrieval quality.
- Halting pipeline on failure — a single faulty image blocks the entire ingestion process.

**Consequence:**
- Inconsistent data is flagged with `needs_review` — enabling manual inspection.
- Failed images are isolated, preserving pipeline robustness.
- Related files: `vision_pipeline.py`

**Status:** Confirmed

## 19) Vision Pipeline: Static Page Allow-List and Pre-Flight Filtering
**Decision:** A static `INGEST_ALLOWLIST` was defined for ~22 pages with diagnostic value out of ~110 images. Additionally, file size (`< 5 KB`) and caption keyword filters (`_SKIP_CAPTION_KEYWORDS`) prevent unnecessary LLM calls.

**Reasoning:**
- Sending all images to the vision LLM unnecessarily inflated token costs.
- Photographs, logos, and equipment mounting images carry no diagnostic value.
- Images below 5 KB are typically icons or decorative elements.
- `_SKIP_CAPTION_KEYWORDS`: "equipment", "photograph", "courtesy", "logo", "photo of", "installed", "mounting", "accessories".

**Alternatives considered:**
- Processing all images — unnecessary cost, low-value data.
- Size filter only — meaningful small diagrams could be missed; keyword filter only — large irrelevant images could slip through.

**Consequence:**
- LLM call costs reduced by ~80%.
- The allowlist must be updated when new documents are added — maintenance overhead.
- Related files: `vision_pipeline.py`

**Status:** Confirmed

## 20) Vision Pipeline: Visual Reasoning (CoT) Parameter
**Decision:** A `visual_reasoning` parameter was added to the vision chunk schema to establish a Chain-of-Thought mechanism. Tailored step-by-step inspection instructions are provided for each schema type.

**Reasoning:**
- In prompts requesting direct outputs, the LLM produced superficial or erroneous results.
- With the CoT approach, the model first analyzes axis units, peak locations, and waveforms step-by-step before reaching a conclusion.
- Customized reasoning instructions are provided for each schema type (spectrum, orbit, bearing_stage, severity_chart).

**Alternatives considered:**
- Direct extraction without CoT — superficial analysis, higher error rate.
- Single generic reasoning prompt — details specific to schema types may be missed.

**Consequence:**
- Structured JSON output quality increases — particularly for complex spectrum and orbit figures.
- Token usage increases (due to additional reasoning text) — an acceptable trade-off.
- Related files: `schemas.py`

**Status:** Confirmed

## 21) Ingestion: Hierarchical Section Path (6.2.2 → 6.2 → 6)
**Decision:** A hierarchical context chain in the format `6.2.2 → 6.2 → 6` is constructed based on page and vertical (y) coordinates for tables, images, or text blocks, and attached to all chunks as `section_path`.

**Reasoning:**
- When chunks lacked context, the LLM struggled to understand which section they originated from post-retrieval.
- The hierarchical section_path preserves the chunk's position within the document hierarchy.
- The section chain is presented in a readable format using the " > " separator.

**Alternatives considered:**
- Page number only — section context is lost.
- Flat section title (nearest heading only) — parent section hierarchy is lost.

**Consequence:**
- The LLM knows which section/sub-section the chunk originates from — producing more contextual answers.
- Minimal additional computational overhead on the ingestion pipeline.
- Related files: `section_utils.py`

**Status:** Confirmed

## 22) Ingestion: Section Heading Detection via Font Analysis
**Decision:** Since the PDF lacked built-in TOC/bookmarks, section headings were detected using font analysis: `font_size ≥ 11.0`, bold flag (`flags & 16`), and numbering regex (`^\d+(?:\.\d+)*\s+`).

**Reasoning:**
- The source PDF lacked table of contents or bookmark metadata.
- Combining font size + bold flag + numbering pattern yields high accuracy in heading detection.
- Headings in the "6.2.1 Bearing Defects" format are captured using the `_HEADING_PATTERN` regex.

**Alternatives considered:**
- PDF bookmark/outline — unavailable in the document structure.
- Font size only — non-bold large fonts produce false positives.
- Heading extraction with LLM — excessively high cost and latency.

**Consequence:**
- Heading detection is executed deterministically in milliseconds.
- Font thresholds may need tuning for PDFs with different formatting.
- Related files: `section_utils.py`

**Status:** Confirmed

## 23) Generation: Exponential Backoff and Gemini Fallback
**Decision:** A 3-attempt exponential backoff (`sleep_time = 2.0 × 2^attempt`) is applied on Groq API rate limits (429) or other errors. If retries are exhausted, the system gracefully falls back to the Gemini model (`gemini-3.5-flash`) without crashing.

**Reasoning:**
- Groq's aggressive rate limiting frequently generated 429 errors under heavy usage.
- Exponential backoff ensures automatic recovery during transient rate limit conditions.
- Gemini fallback guarantees that the system remains operational even if Groq becomes entirely unavailable.

**Alternatives considered:**
- Fixed sleep duration — fails to adapt to rate limit windows.
- No fallback — system crashes when Groq is unavailable.
- Different fallback provider (e.g., OpenAI) — Gemini is more cost-effective and already present in the project.

**Consequence:**
- Automatic recovery from temporary API outages.
- Zero-downtime guarantee via Gemini fallback during persistent outages.
- Gemini output format may slightly differ from Groq — minor format differences are tolerated.
- Related files: `client.py`

**Status:** Confirmed

## 24) DSP: Fault Consolidation via pick_primary_fault and Weak Candidate Notification
**Decision:** Spectrum, envelope, and reciprocating machine analyses are consolidated via `pick_primary_fault` to score primary and secondary faults. Candidates that are weak or potentially noise-induced (`weak_candidates`) are segregated and passed to the LLM system prompt with an explicit advisory note.

**Reasoning:**
- Results from a single analysis source are insufficient — multiple analysis methods must cross-validate one another.
- Candidates meeting multi-harmonic (`n_harmonics ≥ 2`) and sufficient confidence (`confidence ≥ 0.40`) criteria are categorized into `all_faults`, while the rest are moved to `weak_candidates`.
- Rather than hiding weak candidates entirely, they are reported to the LLM as "secondary indicators with suspected noise."

**Alternatives considered:**
- Removing weak candidates completely — potential early-stage faults could be missed.
- Presenting all candidates with equal confidence — the LLM might report weak candidates as definitive faults.

**Consequence:**
- The LLM uses cautious language rather than reporting weak candidates as definitive faults.
- Early-stage fault symptoms are presented transparently rather than hidden.
- Related files: `fault_analyzer.py`, `prompt_builder.py`

**Status:** Confirmed

## 25) Generation: Automatic Initial Query (build_initial_signal_query)
**Decision:** When the user query is empty and live DSP data is available, a standard diagnostic prompt including RMS, Peak, Crest Factor, Kurtosis, ISO zone, and fault detection is automatically constructed via `build_initial_signal_query`.

**Reasoning:**
- Users often uploaded signal files and wanted to use the system without knowing what specific question to ask.
- The automated query feeds DSP results directly to the LLM, guaranteeing a meaningful initial response.
- Machine name, measurement point, ISO zone, and time-domain metrics are automatically included in the query.

**Alternatives considered:**
- Forcing the user to enter a query — degrades UX, as the user may not know what to ask.
- Generic "analyze this" prompt — lacks DSP results, causing the LLM to operate without context.

**Consequence:**
- Zero-input UX: Users obtain a meaningful diagnosis simply by uploading a signal.
- The automated query injects pick_primary_fault and ISO assessment results directly into the LLM context.
- Related files: `prompt_builder.py`, `main_graph.py`

## 26) Generation: Epistemic Refusal Behavior (Honest Statement of Missing Information)
**Decision:** A rule was established requiring the model to honestly state "no information is available in the context" when documentation lacks relevant information. In the self-corrector verification prompt, this honest refusal behavior is not penalized as an omission, and is evaluated with a faithfulness score of `0.95` and relevance score of `1.0`.

**Reasoning:**
- LLMs tend to hallucinate when context lacks information — dangerous in industrial diagnosis.
- Saying "no information" is correct behavior — the self-corrector should not penalize it.
- Epistemic refusal is detected using 12 distinct refusal phrase patterns.

**Alternatives considered:**
- Penalizing refusal behavior — forces the LLM to hallucinate.
- Automatic retrieval expansion on refusal — not always possible and may lead to infinite loops.

**Consequence:**
- Hallucination risk is reduced — the LLM is permitted to say "I don't know."
- The self-corrector avoids unnecessary retry loops in this scenario.
- Related files: `prompts.yaml`, `checkers.py`

**Status:** Confirmed

## 27) Retrieval: Parent-Child Chunking Strategy (Qdrant + SQLite)
**Decision:** A two-tier Parent-Child chunking strategy was adopted: ~1500 token Parent chunks are stored in an SQLite (`docstore.db`)-based DocStore, while ~200 token Child chunks are stored in a Qdrant vector database (`vibra_text_child` collection). During retrieval, search is performed over child chunks, and the parents of retrieved child chunks are fetched from DocStore to provide full context to the LLM.

**Reasoning:**
- Small child chunks provide more accurate semantic matching with dense/sparse embeddings.
- Large parent chunks provide sufficient context to the LLM, supporting more coherent answer generation.
- SQLite is sufficient as a lightweight key-value store for parent chunks — requiring no additional database infrastructure.
- Qdrant's native hybrid search (dense + sparse prefetch + RRF fusion) optimizes child chunk retrieval.

**Alternatives considered:**
- Single-tier chunking (small chunks only) — insufficient LLM context.
- Single-tier chunking (large chunks only) — inferior embedding quality.
- Storing all chunks in Qdrant — calculating vectors for parent chunks introduces unnecessary overhead.
- PostgreSQL/Redis parent store — overkill for MVP.

**Consequence:**
- Retrieval: high precision (small child chunk matching) + high recall (large parent context).
- SQLite is simple and portable; however, migration should be planned if scaling is required.
- Related files: `docstore.py`, `qdrant_vector_db.py`, `build_db.py`, `retriever.py`

**Status:** Confirmed

## 28) Generation: Primary LLM Generator Model Selection (openai/gpt-oss-120b via Groq)
**Decision:** `openai/gpt-oss-120b` served via Groq LPU inference was selected as the primary response generator model. The model configuration in `app.yaml` is set with `provider: "groq"`, `model: "openai/gpt-oss-120b"`, `temperature: 0.2`, `max_tokens: 4096`, and `reasoning_format: "parsed"`.

**Reasoning:**
- Industrial vibration diagnosis requires deep multi-step kinematic reasoning across spectral metrics (harmonics, sidebands, kurtosis, crest factor, ISO severity boundaries).
- The 120B parameter capacity of `openai/gpt-oss-120b` provides superior reasoning depth and instruction adherence over smaller open-source models, preventing subtle diagnostic confusions.
- Groq's high-throughput LPU infrastructure delivers low-latency token streaming despite the 120B parameter scale.
- Chain-of-thought `<think>` tags produced during internal reasoning are cleanly filtered and parsed (`reasoning_format: "parsed"` / `_clean_reasoning_tags`) to present clear, professional, structured diagnostic reports without prompt/reasoning leakage.

**Alternatives considered:**
- Smaller parameter models (`Qwen 2.5 72B` / `Llama 3.3 70B`) — slightly faster but exhibited lower reasoning fidelity on complex overlapping kinematic fault scenarios.
- Closed-source proprietary APIs (e.g. GPT-4o, Claude 3.5 Sonnet) — higher per-token costs and unpredictable latency compared to Groq-hosted open weights.

**Consequence:**
- Enhanced diagnostic quality, structured root-cause maintenance advisories, and strict compliance with domain rules.
- Near-instantaneous response times maintained via Groq inference.
- Clean user-facing output with internal reasoning tokens stripped.
- Related files: `app.yaml`, `client.py`, `main_graph.py`, `prompt_builder.py`

**Status:** Confirmed
